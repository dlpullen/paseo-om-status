# OM status on Paseo 0.17.4

This is the contract check requested in [HANDOFF.md](../HANDOFF.md). It covers the installed daemon and SDK (both 0.17.4), the matching [Paseo client source at v0.17.4](https://github.com/getpaseo/paseo/tree/v0.17.4/packages/app), and `pi-observational-memory` 3.1.4. The approved shipping placement is the stock track bar; no Paseo fork is needed.

## Placement and popover

- `addComposerPill({ id, workspaceId, agentId, button })` is per agent. Its `popover` behavior supplies an anchored surface with typed host, workspace and agent props. The app owns trigger styling (including the upward chevron), top/start anchoring, and the compact bottom sheet. See the [button SDK](https://github.com/getpaseo/paseo/blob/v0.17.4/packages/plugin/src/client/buttons.ts) and [client implementation](https://github.com/getpaseo/paseo/blob/v0.17.4/packages/app/src/plugins/buttons/view.tsx).
- The app renders plugin pills in [`AgentTracks`](https://github.com/getpaseo/paseo/blob/v0.17.4/packages/app/src/panels/agent-tracks.tsx), alongside Tasks and Subagents, not in the composer footer. The [context meter](https://github.com/getpaseo/paseo/blob/v0.17.4/packages/app/src/composer/index.tsx) enters the [right footer group](https://github.com/getpaseo/paseo/blob/v0.17.4/packages/app/src/composer/input/input.tsx) via `beforeVoiceContent`. The pill contract has no placement or alignment option. `addComposerItem` is not a substitute: it appears in the [left agent controls](https://github.com/getpaseo/paseo/blob/v0.17.4/packages/app/src/composer/agent-controls/index.tsx) or their compact/overflow sheet.
- A stock plugin can render the mockup's **content** from the track bar without moving or covering the Pi meter. Exact footer placement requires a Paseo app/SDK change. Prefer an opt-in slot immediately before the meter that reuses the existing button host and leaves existing pills in the track. Do not hide, move, or repurpose the meter to approximate the layout. The stock compact sheet and wide anchoring are host-owned; check whether the new slot also needs an alignment option against the approved screenshots.

## Selected live session and status

The pill's `agentId` is a Paseo ID, not a Pi session ID. `PluginAgentSnapshot` does not include the latter. The host-scoped SDK's `paseo.agents.ref(agentId).refresh()` is a snapshot read (`fetch_agent_request`); it does not reopen the agent. The returned `PaseoAgent` exposes `runtimeInfo.sessionId` and `persistence.sessionId`. In the installed daemon's `agent/providers/pi/agent.js`, `getRuntimeInfo()` refreshes Pi state and returns its `sessionId`; `describePersistence()` is a persisted handle and can refer to a session file other than the live runtime's copy. Use the live ID, validated against a live bridge registration. Do not substitute a persisted ID, path, cwd match, or another agent's data. The snapshot alone is not proof of liveness: the same request can return a settled record. `reload()` is not a status operation; it reopens the provider and can interrupt a turn.

There is **no built-in read-only structured OM status route** in the installed contracts. Pi's `get_state` and `get_session_stats` are native Pi data; `get_commands` only lists commands. OM 3.1.4's `src/commands/status.ts` computes from the active `ctx.sessionManager.getBranch()`, its extension's `Runtime`/configuration and `ctx.model?.contextWindow`, then calls `ctx.ui.notify`. Neither the SDK command list nor those Pi RPCs expose the result. Do not send `/om:status` via the composer, SDK `send`/`run`, or another prompt transport. Paseo 0.17.4's Pi provider `completeNoTurnPrompt` still calls `emitBufferedNoTurnOutputs`, which emits a user timeline row and, when present, notification output as assistant rows. No model invocation is not the same as no chat changes.

## Implemented adapter

The long-term seam is a versioned, structured in-process reader exposed by OM itself, with `/om:status` formatting that same result. OM 3.1.4 does not have one. Until it does, the companion declares OM 3.1.4 as a [Pi package dependency](https://pi.dev/docs/latest/packages#declare-dependencies), loads its factory from its own module tree, and captures the audited status handler at registration. The normal Pi Git install resolves OM automatically; a separately registered standalone copy is not part of this dependency. It calls that handler directly with the live cwd, model and read-only branch, and captures `notify` in memory. It strictly decodes just that output into the structured wire format. No call goes through Pi's command dispatcher, Paseo's prompt path, or the transcript. No formulas or token budgets are copied; the normal manual command is registered unchanged. No installed package is patched.

1. [`index.server.ts`](../index.server.ts) creates a private per-launch directory and passes its address in `agent.open.before` for interactive Pi only. This hook cannot inject an extension file. A status request never starts or reopens a session.
2. [`pi/index.ts`](../pi/index.ts) binds its socket to Pi's `ctx.sessionManager.getSessionId()` and a fresh revision for every `session_start`. `session_shutdown` invalidates the binding and closes the socket before a new session can bind. The socket exposes only read/status identity, no arbitrary command, prompt or file operations.
3. [`server/bridge.ts`](../server/bridge.ts) verifies the exact agent, workspace, provider and live runtime session ID before and after sampling. It checks the current launch path and the socket's current session revision, even when a reopen reuses the same persisted ID. The output carries no paths or capabilities.
4. [`index.client.tsx`](../index.client.tsx) maintains one pill per applicable Pi agent on the host. The client drops superseded requests, clears old values on a known session or model change, shows unavailable on failed reads and removes the numeric value when a sample expires. Other providers do not get a pill. The displayed percentages are OM's values; only the progress-bar width is visually clamped.

OM 3.1.4 status was verified on both Pi 0.84.2 and the daemon's installed Pi 1.6.1 executable. The initial TypeScript failure when checking the full OM source against npm-resolved Pi 1.6.1 declarations was not a runtime failure: Pi's extension loader successfully loads the installed OM package. The companion accepts both verified Pi versions and fails closed for others. No live installation or provider configuration was changed. See [setup](../README.md#install-from-github).

Web smoke tests open and refresh at 1400 px and 390 px, confirm the independent context meter is present, and require no timeline changes. Native clients were not exercised.
